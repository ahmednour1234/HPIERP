## (1) الزيارات — جاهز

`GET /visits/results` يرجّع المنطقة والتخصص داخل `customer`، ويقبل الفلترة من
السيرفر. **يمكن حذف الـ workaround الذي يجلب كل العملاء (200 عميل).**

```json
"customer": {
  "id": 1434, "name": "تجربة2", "mobile": "333",
  "region_id": 15,
  "region":   { "id": 15, "name": "الفيوم" },
  "category_id": 46,
  "category": { "id": 46, "name": "اطفال عام" }
}
```

| Param | مثال |
|---|---|
| `from` / `to` | `2026-09-01` / `2026-09-30` |
| `region_id` | `5` |
| `category_id` | `3` |

```
GET /api/v2/visits/results?from=2026-09-01&to=2026-09-30&region_id=5&category_id=3
```

`region_id` و`category_id` يقبلان قيمة واحدة أو مصفوفة.

> `category_id` هو التخصص الطبي (`categories.type = 0`). وعمود `customers.specialist`
> شيء آخر يحمل نوع الجهة (صيدلية / مركز / مستشفى / طبيب)، فلا يصلح للفلترة بالتخصص.

**صورة الزيارة** (الملاحظة الإضافية) موجودة أيضًا: الرد يحمل `img` و`img_url`
برابط كامل، أو `null` حين لا توجد صورة.

## (2) سعر المنتج للعميل — جاهز

`GET /stocks` يقبل `customer_id`، فيرجّع سعر العميل في نفس الطلب.
**يمكن حذف الاستدعاء المنفصل لـ `POST /products/customer-prices`.**

```
GET /api/v2/stocks?type=4&customer_id=1434
```
```json
"product": {
  "id": 88, "name": "فوليك أسيد",
  "selling_price": 79,
  "customer_price": 69
}
```

حقل `customer_price` موجود دائمًا في الرد، وقيمته `null` حين لا يُمرَّر
`customer_id` أو حين لا يكون للعميل سعر متفاوض عليه — فلا حاجة لفحص وجود
المفتاح. **السعر الأساسي `selling_price` يبقى كما هو ولا يُستبدل**، ليظل
الفرق ظاهرًا للمندوب.

> عن `selling_price = 0`: القيمة تأتي من عمود `products.selling_price`. إن كانت
> صفرًا لمنتج بعينه فالبيانات نفسها هي ما تحمل صفرًا (والسعر مكتوب في اسم
> المنتج يدويًا) — لا يصلحه الـ API. أرسلوا لنا أكواد المنتجات المتأثرة
> لنصحّح صفوفها في قاعدة البيانات.

## (3) إرجاع البضاعة بموافقة الأدمن — تم تنفيذه

المندوب يحدد ما يرجعه، ويُسجَّل الطلب معلّقًا. **لا يتحرك المخزون إطلاقًا قبل
اعتماد الأدمن.**

### أ) `POST /stocks/confirm`

| Field | Rules |
|---|---|
| `items` | required, array, min 1 |
| `items.*.product_id` | required, integer, موجود في العربية |
| `items.*.quantity` | required, integer, min 1 |
| `note` | nullable, string, max 2000 |

يرد **201**:

```json
{
  "success": true,
  "message": "Stock return request submitted for approval",
  "data": {
    "id": 77,
    "status": "pending",
    "status_text": "بانتظار الموافقة",
    "note": "باقي اليوم",
    "admin_note": null,
    "reviewed_at": null,
    "created_at": "2026-09-11T14:20:00+03:00",
    "items": [
      { "product_id": 812, "quantity": 6,
        "product": { "id": 812, "name": "فوليك أسيد", "product_code": "P-812" } }
    ]
  }
}
```

| الحالة | الكود |
|---|---|
| كمية تتجاوز المتاح، أو منتج ليس في العربية | `422` |
| للمندوب طلب معلّق بالفعل | `409` |

### ب) `GET /stocks/confirm/current`

آخر طلب: المعلّق إن وُجد، وإلا آخر ما رُوجع. حين لا يوجد أي طلب يرد
`{"data": null}` بحالة 200 — وهو ما يخبر التطبيق أن يعرض فورم الاختيار.

بعد المراجعة يحمل الرد `admin_note` و`reviewed_at`، فيمكن عرض سبب الرفض.

### ج) `POST /stocks/confirm/{id}/cancel`

سحب طلب معلّق قبل المراجعة. `409` بعد المراجعة، و`404` لطلب مندوب آخر
(لا `403`، حتى لا يكشف الرد وجوده).

### د) جهة الأدمن

شاشة في اللوحة على `admin/stock-returns`: قائمة بالطلبات (المعلّقة أولًا)
وشاشة مراجعة فيها **اعتماد** (ينقل الكميات من العربية إلى المخزن في معاملة
واحدة) و**رفض** (يسجّل السبب، والمخزون لا يتغير).

### الحماية من ازدواج الخصم

أربع قواعد تمنع خصم الكمية مرتين:

1. **طلب معلّق واحد لكل مندوب** — إرسال الطلب مرتين يُرفض بـ 409.
2. **قفل الصفوف وقت الاعتماد** — اعتمادان متزامنان لا يمران معًا.
3. **إعادة الفحص وقت المراجعة** — العربية قد تتغير بين الطلب والاعتماد؛ إن لم
   تعد الكمية متاحة يُرفض الاعتماد بالكامل ولا يُكتب شيء.
4. **جمع السطور المكررة** — سطران لنفس المنتج يُجمعان قبل الفحص، وإلا مرّ كل
   سطر وحده بينما مجموعهما يتجاوز المتاح.

### ⚠️ تغيير سلوك

`POST /api/v2/stocks/confirm` صار **يتطلب `items`** ويرد **201** بدل 200.
الطلب بلا body يرد 422.

التسوية الفورية القديمة باقية على **`POST /api/v1/stocks/confirm`**، وهي التي
تكتب السجلات التي يقرأها `GET /stocks/history`.

## ما لم يُنفَّذ

**الإشعار للمندوب عند المراجعة.** الأدمن يعتمد أو يرفض، لكن لا يصل إشعار.
أخبرونا بنظام الإشعارات المستخدم في التطبيق (Firebase / OneSignal / غيرهما)
وأين يُخزَّن الـ device token، ونوصّله.

في الوقت الحالي يعرف التطبيق النتيجة من `GET /stocks/confirm/current` عند فتح
الشاشة.
