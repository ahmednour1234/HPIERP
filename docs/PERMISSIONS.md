# الأدوار والصلاحيات

نظام صلاحيات قائم على الأدوار، حلّ محل 33 عمودًا منطقيًا كانت على جدول
`admins`.

## لماذا تغيّر

| قبل | بعد |
|---|---|
| 33 عمودًا منطقيًا على `admins` | جداول `roles` / `permissions` |
| إضافة صلاحية = هجرة جديدة | صف في `permissions` |
| لا تجميع: كل أدمن يُضبط وحده | دور يُعاد استعماله |
| قسم كامل يُمنح أو يُمنع | فعل بفعل: عرض / إضافة / تعديل / حذف / تصدير |
| **26 مسارًا محميًا من 327** | **320 مسارًا، كلها** |

الأخطر أن الحماية كانت في القائمة الجانبية وحدها: الروابط تُخفى، لكن
كتابة `admin/account/list` تفتح الحسابات لأي أدمن مسجَّل. أُثبت ذلك قبل
التعديل على حساب بلا صلاحيات، وصار الآن يردّ `403`.

## البنية

```
permissions        الصلاحيات المتاحة (155)، مزروعة من App\Support\Permissions
roles              الأدوار
permission_role    صلاحيات كل دور
role_admin         أدوار كل مستخدم
```

اسم الصلاحية `<المجموعة>.<الفعل>` — مثل `accounts.view` و`invoices.export`.
و`system.super` تفتح كل شيء ويملكها دور «مدير عام» وحده.

## الاستعمال

### في المسارات

```php
// صلاحية بعينها
Route::get('roles', ...)->middleware('permission:roles.view');

// أي واحدة من عدة صلاحيات
Route::post('x', ...)->middleware('permission:accounts.create,accounts.update');
```

كل مسارات `admin/` محروسة تلقائيًا بـ `section.permission`، الذي يستنتج
القسم من بادئة الرابط (`admin/account/**` ← `accounts`). الأخص يسبق الأعم،
فـ `admin/pos/installments` تخص التحصيلات لا الفواتير، و`admin/admin/salaries`
تخص المرتبات لا المستخدمين.

**كل المسارات مصنَّفة** — 320 مسارًا على 38 قسمًا، ولا يمرّ بلا فحص إلا
تسجيل الدخول والخروج والصفحة الترحيبية. ما لا تصنيف له **يُمنع**: مسار
جديد نُسي تصنيفه يظهر فورًا بدل أن يبقى مفتوحًا بصمت.

البادئات في `EnforceSectionPermission::PREFIX_MAP`. عند إضافة قسم جديد:

1. أضف المجموعة إلى `App\Support\Permissions::groups()`
2. أضف بادئة الرابط إلى `PREFIX_MAP`
3. `php artisan db:seed --class=RolesPermissionsSeeder` لزرع الصلاحيات
4. احرس القسم في القائمة الجانبية بـ `@cangroup`

`RouteCoverageTest` يسقط إن نُسيت الخطوة الثانية.

### في القوالب

```blade
@cangroup('accounts')        {{-- أي صلاحية في القسم: للقائمة الجانبية --}}
@endcangroup

@haspermission('accounts.create')   {{-- فعل بعينه: لإخفاء زر --}}
@endhaspermission

@hasanypermission(['a.view', 'b.view'])
@endhasanypermission
```

> ضع الوسم الختامي في سطر مستقل. Blade لا يصرّف التوجيه إن تلاه حرف
> مباشرةً مثل `]`، فيظهر نصًّا في الصفحة.

`@can` المدمجة لا تصلح هنا: تسأل حارس `web` الافتراضي، واللوحة تسجّل
الدخول على حارس `admin`، فترجع `false` دائمًا. (بوابة `Gate::before`
مسجّلة أيضًا، فـ `Gate::forUser($admin)->allows('x')` تعمل في الكود.)

### في الكود

```php
$admin->hasPermission('accounts.view');
$admin->hasAnyPermission(['a.view', 'b.view']);
$admin->canAccessGroup('accounts');
```

## الشاشات

- `admin/roles` — الأدوار
- `admin/roles/create` — دور جديد بشبكة صلاحيات لكل قسم
- `admin/roles/assign` — إسناد الأدوار للمستخدمين

## الترحيل

`RolesPermissionsSeeder` يُشغَّل مرة واحدة فيزرع الصلاحيات ويحوّل الأعمدة
القديمة:

```bash
php artisan migrate
php artisan permissions:sync
```

`permissions:sync` يغلّف البذرة ويعرض بعدها الحالة، وأهمها من لا دور له —
مستخدم بلا دور لا يرى شيئًا، وهي حالة صامتة يصعب تشخيصها. و`--show` يعرض
الحالة دون كتابة:

```bash
php artisan permissions:sync --show
```

## منح كل الصلاحيات من السطر

الشاشة لا تكفي دائمًا: لو لم يبق في النظام من يفتح `admin/roles` فلا سبيل
لمنح أحد شيئًا منها. `permissions:super` هو الباب المقصود لذلك، ويُشغَّل
على الخادم:

```bash
php artisan permissions:super admin2@gmail.com     # بالبريد
php artisan permissions:super 100                  # أو بالرقم
php artisan permissions:super --list               # من هم السوبر أدمنز الآن
php artisan permissions:super 100 --revoke         # سحب الصلاحية
```

البريد يُطابق جزئيًا أيضًا، فبعض الحسابات تحمل لواحق مثل
`admin2@gmail.com00`. ولو طابق النص أكثر من مستخدم فالأمر يفشل ويعرضهم
بدل أن يخمّن.

المنح يضيف دور `super-admin` ولا يمسّ بقية الأدوار، فالسحب يعيد المستخدم
إلى ما كان عليه لا إلى لا شيء. الدور يحمل `system.super` التي يمرّرها
`Gate::before` على كل شيء، فأي قسم يُضاف لاحقًا يراه صاحبه دون إعادة منح.

الأمر يفشل برمز خروج غير صفري إن لم يوجد المستخدم أو لم تُشغَّل البذرة
بعد، فيصلح داخل سكربت نشر.

البذرة مستدعاة أيضًا من `DatabaseSeeder` بعد بذور البيانات، فالتركيب من
الصفر يخرج بأدوار جاهزة. تشغيلها مرارًا آمن: لا تكرّر صفًّا ولا تمحو
تعديلًا أُجري على دور.

لكل أدمن دور باسم `legacy-admin-<id>` يحمل ما كان يملكه بالضبط، فلا يفقد
أحد وصوله لحظة تفعيل الفحص. الأدوار المولَّدة قابلة للتعديل والاستبدال،
والتشغيل مرارًا لا يلغي تعديلًا أُجري عليها.

**الأعمدة القديمة لم تُحذف.** ما زالت على `admins` ولا يقرأها النظام
الجديد إلا في الترحيل. احذفها بهجرة منفصلة بعد التأكد من استقرار النظام —
حذفها الآن يمنع أي رجوع.

## ملاحظات

- `is_super` يتجاوز كل فحص، ويبقى عاملًا للبيانات القائمة.
- مستخدم بلا دور لا يرى شيئًا: أسند له دورًا واحدًا على الأقل.
- دور «مدير عام» مقفل: لا يُحذف ولا تُعدَّل صلاحياته، وإلا بقي النظام بلا
  من يدير الأدوار.
- دور مسند إلى مستخدمين لا يُحذف حتى يُنقلوا إلى غيره.
