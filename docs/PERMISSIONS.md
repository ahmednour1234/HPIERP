# الأدوار والصلاحيات

نظام صلاحيات قائم على الأدوار، حلّ محل 33 عمودًا منطقيًا كانت على جدول
`admins`.

## لماذا تغيّر

| قبل | بعد |
|---|---|
| 33 عمودًا منطقيًا على `admins` | جداول `roles` / `permissions` |
| إضافة صلاحية = هجرة جديدة | صف في `permissions` |
| لا تجميع: كل أدمن يُضبط وحده | دور يُعاد استعماله |
| قسم كامل يُمنح أو يُمنع | فعل بفعل: عرض / إضافة / تعديل / حذف / تصدير |
| **26 مسارًا محميًا من 327** | كل مسارات اللوحة |

الأخطر أن الحماية كانت في القائمة الجانبية وحدها: الروابط تُخفى، لكن
كتابة `admin/account/list` تفتح الحسابات لأي أدمن مسجَّل. أُثبت ذلك قبل
التعديل على حساب بلا صلاحيات، وصار الآن يردّ `403`.

## البنية

```
permissions        الصلاحيات المتاحة (119)، مزروعة من App\Support\Permissions
roles              الأدوار
permission_role    صلاحيات كل دور
role_admin         أدوار كل مستخدم
```

اسم الصلاحية `<المجموعة>.<الفعل>` — مثل `accounts.view` و`invoices.export`.
و`system.super` تفتح كل شيء ويملكها دور «مدير عام» وحده.

## الاستعمال

### في المسارات

```php
// صلاحية بعينها
Route::get('roles', ...)->middleware('permission:roles.view');

// أي واحدة من عدة صلاحيات
Route::post('x', ...)->middleware('permission:accounts.create,accounts.update');
```

كل مسارات `admin/` محروسة تلقائيًا بـ `section.permission`، الذي يستنتج
القسم من بادئة الرابط (`admin/account/**` ← `accounts`). الأخص يسبق الأعم،
فـ `admin/pos/installments` تخص التحصيلات لا الفواتير.

ما لا بادئة له يمرّ: الغرض سدّ الأقسام المعروفة لا قفل اللوحة وكسر شاشات
لم تُصنَّف. البادئات في `EnforceSectionPermission::PREFIX_MAP`.

### في القوالب

```blade
@cangroup('accounts')        {{-- أي صلاحية في القسم: للقائمة الجانبية --}}
@endcangroup

@haspermission('accounts.create')   {{-- فعل بعينه: لإخفاء زر --}}
@endhaspermission

@hasanypermission(['a.view', 'b.view'])
@endhasanypermission
```

> ضع الوسم الختامي في سطر مستقل. Blade لا يصرّف التوجيه إن تلاه حرف
> مباشرةً مثل `]`، فيظهر نصًّا في الصفحة.

`@can` المدمجة لا تصلح هنا: تسأل حارس `web` الافتراضي، واللوحة تسجّل
الدخول على حارس `admin`، فترجع `false` دائمًا. (بوابة `Gate::before`
مسجّلة أيضًا، فـ `Gate::forUser($admin)->allows('x')` تعمل في الكود.)

### في الكود

```php
$admin->hasPermission('accounts.view');
$admin->hasAnyPermission(['a.view', 'b.view']);
$admin->canAccessGroup('accounts');
```

## الشاشات

- `admin/roles` — الأدوار
- `admin/roles/create` — دور جديد بشبكة صلاحيات لكل قسم
- `admin/roles/assign` — إسناد الأدوار للمستخدمين

## الترحيل

`RolesPermissionsSeeder` يُشغَّل مرة واحدة فيزرع الصلاحيات ويحوّل الأعمدة
القديمة:

```bash
php artisan migrate
php artisan db:seed --class=RolesPermissionsSeeder
```

لكل أدمن دور باسم `legacy-admin-<id>` يحمل ما كان يملكه بالضبط، فلا يفقد
أحد وصوله لحظة تفعيل الفحص. الأدوار المولَّدة قابلة للتعديل والاستبدال،
والتشغيل مرارًا لا يلغي تعديلًا أُجري عليها.

**الأعمدة القديمة لم تُحذف.** ما زالت على `admins` ولا يقرأها النظام
الجديد إلا في الترحيل. احذفها بهجرة منفصلة بعد التأكد من استقرار النظام —
حذفها الآن يمنع أي رجوع.

## ملاحظات

- `is_super` يتجاوز كل فحص، ويبقى عاملًا للبيانات القائمة.
- مستخدم بلا دور لا يرى شيئًا: أسند له دورًا واحدًا على الأقل.
- دور «مدير عام» مقفل: لا يُحذف ولا تُعدَّل صلاحياته، وإلا بقي النظام بلا
  من يدير الأدوار.
- دور مسند إلى مستخدمين لا يُحذف حتى يُنقلوا إلى غيره.
